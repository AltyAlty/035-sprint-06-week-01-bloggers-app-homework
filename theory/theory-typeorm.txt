TypeORM предоставляет следующий функционал:
1. Mapping - это преобразование записей из PostgreSQL в JS-объекты и обратно.
2. Change detection - это механизм отслеживания изменений объекта.
3. Подход Code-first -> SQL schema - это подход, при котором сначала в коде описываются сущности БД, а уже потом на
основе этого кода автоматически создаются SQL-схемы.
4. Миграции - это механизм контроля изменений схемы БД во времени. Вместо автоматической синхронизации структуры при
помощи опции "synchronize: true" разработчик создает файлы миграций, содержащие SQL-команды для изменения схемы, что
позволяет версионировать структуру БД вместе с кодом, откатывать изменения и безопасно применять их на разных
окружениях.
5. Возможно реализовать паттерн "репозиторий".
6. QueryBuilder - это функционал, позволяющий генерировать сложные SQL-запросы путем программного построения через
цепочку методов, когда паттерна "репозиторий" для этого недостаточно.
7. Быстрое переключение между разными реляционными БД.

/*--------------------------------------------------------------------------------------------------------------------*/

TypeORM не всегда может преобразовать сложный запрос в тот, который именно нужен.

/*--------------------------------------------------------------------------------------------------------------------*/

Для настройки подключения к PostgreSQL нужно использовать методы "TypeOrmModule.forRoot()" или
"TypeOrmModule.forRootAsync()" из модуля @nestjs/typeorm.

/*--------------------------------------------------------------------------------------------------------------------*/

Для написаний сырых запросов для PostgreSQL можно использовать класс "DataSource" из TypeORM, путем внедрения его
экземпляров в конструкторы классов репозиториев при помощи декоратора "@InjectDataSource()" из модуля @nestjs/typeorm.

/*--------------------------------------------------------------------------------------------------------------------*/

Для создания сущностей TypeORM предоставляет следующие декораторы:
1. "@Entity()": помечает класс как сущность, связанную с таблицей БД, в качестве опции принимая имена таблицы и схемы.
2. "@Check()": создает ограничение "CHECK" на уровне таблицы, принимая сырой SQL.
3. "@Unique()": создает ограничение "UNIQUE" на одну или несколько колонок, принимая имена свойств класса, а не колонок
БД.
4. "@PrimaryGeneratedColumn()": создает первичный ключ формата "UUID" или "SERIAL ID", автоматически генерируемый БД.
5. "@PrimaryColumn()": создает первичный ключ без автогенерации.
6. "@Column()": создает поле таблицы, принимая объект с опциями для поля.
7. "@CreateDateColumn()": создает поле, которое автоматически заполняется датой при вставке записи, принимая объект с
опциями для поля.
8. "@DeleteDateColumn()": создает поле для soft удаления, позволяя пользоваться методом "softDelete()", а все методы
поиска автоматически используют "deleted_at IS NULL".
9. "@OneToMany()": реализует отношение один ко многим, не создавая новых полей, для использования для навигации и
параметра "relations" в запросах. Требует использования декоратора "@ManyToOne()" в парной сущности.
10. "@ManyToOne()": реализует отношение многие к одному. Требует использования декоратора "@OneToMany()" в парной
сущности.
11. "@JoinColumn()": уточняет, какое поле является FK и на какое поле целевой таблицы оно ссылается. Используется вместе
с декоратором "@ManyToOne".
12. "@VersionColumn()": реализует оптимистическую блокировку (Optimistic Locking) для защиты данных от перезаписи при
одновременном редактировании.
13. "@ManyToMany": реализует отношение многие ко многим, указывая, что записи обеих таблиц могут ссылаться друг на друга
многократно.
14. "@JoinTable": создает промежуточную таблицу из двух колонок с FK для реализации связи через декоратор "@ManyToMany"
в БД. Ставится только на владеющей стороне связи, то на стороне сущности, которая решает когда создавать, обновлять или
удалять связь между записями.
15. "@OneToOne()": реализует отношение один к одному.

В декораторах "@OneToOne()" и "@OneToMany()" можно указывать опцию "orphanedRowAction", определяющую, что TypeORM должен
делать с дочерними записями, которые раньше были привязаны к родителю, но после обновления родителя были убраны из его
массива в коде и больше не принадлежит ни одному родителю, когда такие записи удаляют из массива родительской сущности
при каскадном сохранении.

В декораторах, которые реализуют отношения между таблицами, можно указывать опцию "cascade" для управления каскадностью
при операциях создания и изменения.

Для регистрации сущностей в соответствующих модулях, а не в модуле "AppModule", нужно использовать метод
"TypeOrmModule.forFeature()" из модуля @nestjs/typeorm, указывая в нем массив классов для сущностей.

/*--------------------------------------------------------------------------------------------------------------------*/

Для работы с репозиториями TypeORM предоставляет класс "Repository" и модуль @nestjs/typeorm предоставляет декоратор
"@InjectRepository()" для внедрения экземпляров класса "Repository". Если в двух сущностях настроены отношения, то при
использовании методов поиска экземпляров класса "Repository" можно использовать опцию "relations" для получения данных
сразу из двух таблиц. Альтернативой для опции "relations" является опция "eager", главное отличие которой заключается в
том, что она всегда подтягивает данных из других таблиц.

TypeORM предоставляет класс "EntityManager", который можно использовать вместо класса "Repository", внедряя его при
помощи декоратора "@InjectEntityManager()" из модуля @nestjs/typeorm. Класс "Repository" работает на основе класса
"EntityManager" и имеет доступ к последнему через свойство "manager".

Отличия класса "EntityManager" от класса "Repository":
1. Изначально знает обо всех сущностях сразу из-за чего нет необходимости внедрять отдельные репозитории под каждую
таблицу.
2. Позволяет работать сразу с несколькими сущностями в рамках одного контекста, что является очень удобным при работе с
транзакциями.
3. Хуже подходит для DDD и модульной архитектуры, так как размывает границы ответственности и нарушает инкапсуляцию, так
как вместо работы с конкретным агрегатом дает доступ ко всей БД.

Класс "Repository" из TypeORM предоставляет метод "update()", для обновления данных в таблицах. Этот метод особенно
удобен, когда нужно обновить большое количество однотипных элементов. В отличие от метода "save()", метод "update()" не
загружает объект из БД, не запускает хуки, не работает с каскадностью, не использует change detection, но при этом
позволяет массовое обновление данных и работает в таких ситуациях быстрее метода "save()".

/*--------------------------------------------------------------------------------------------------------------------*/

Нужно всегда помнить, что высокоуровневые API, например, классы "Repository" или "QueryBuilder" из TypeORM, могут часто
под капотом очень сильно переусложнять SQL-запросы. Например, класс "QueryBuilder" собирает SQL-запросы по указанными
командам, но может добавлять алиасы и служебные обертки, когда класс "Repository" заставляет ORM самой полностью строить
SQL-запрос, часто создавая через чур переусложненные подзапросы. Поэтому в реальных проектах стоит использовать подход,
когда применяются сразу несколько разных API, предоставляемых ORM.
