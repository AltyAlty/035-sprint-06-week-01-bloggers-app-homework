Переменные окружения - это значения, которые могут быть установлены на уровне операционной системы или приложения и
использоваться для настройки поведения программного обеспечения, например, пароли, ключи API, пути к файлам и так далее.

/*--------------------------------------------------------------------------------------------------------------------*/

"process" - это глобальный объект в Node.js, который содержит информацию о текущем процессе выполнения. "process.env" -
это объект, содержащий все переменные окружения, доступные приложению.

/*--------------------------------------------------------------------------------------------------------------------*/

Переменные окружения можно задать следующими способами:
1. В файлах ".env", настраивающих объект "process.env" из Node.js. Самый низкий приоритет - перебиваются переменными
окружения из других источников, так как библиотека dotenv работает по правилу не перезаписывать то, что уже есть в
объекте "process.env".
2. В ОС.
3. В настройках развертывания приложения через Docker. Могут переопределять переменные окружения из ОС.
4. В команде запуска приложения в терминале. Самый высокий приоритет - перебивают переменные окружения из других
источников.

/*--------------------------------------------------------------------------------------------------------------------*/

Варианты файлов ".env":

1. Файл ".env.example": фиктивные переменные окружения, чтобы предоставить примеры и описание переменных окружения,
используемых в приложении. Не содержит реально используемые данные в приложении.

2. Файл ".env": переменные окружения по умолчанию. Обычно используется для небольших проектов при отсутствии других
более специфичных файлов ".env". Не содержит секретные и чувствительные данные.

3. Файл ".env.development": переменные окружения, используемые при разработке приложения. Обычно не содержит секретные и
чувствительные данные, но если содержит, то указывается в файле ".gitignore".

4. Файл ".env.development.local": переменные окружения для какой-то конкретной машины или разработчика, используемые в
разработке. Имеет более высокий приоритет, чем файл ".env.development". Указывается в файле ".gitignore".

5. Файл ".env.test": переменные окружения, используемые при тестировании приложения. Не содержит секретные и
чувствительные данные.

6. Файл ".env.test.local": переменные окружения для какой-то конкретной машины или разработчика, используемые при
тестировании приложения. Имеет более высокий приоритет, чем файл ".env.test". Обычно не содержит секретные и
чувствительные данные, но если содержит, то указывается в файле ".gitignore".

7. Файл ".env.staging": переменные окружения, используемые в staging-среде (в препродакшене) - в среде, максимально
приближенной к продакшену, для финальной проверки перед релизом. Обычно не содержит секретные и чувствительные данные,
но если содержит, то указывается в файле ".gitignore".

8. Файл ".env.production": переменные окружения, используемые в продакшене. Обычно не содержит секретные и
чувствительные данные, но если содержит, то указывается в файле ".gitignore".

/*--------------------------------------------------------------------------------------------------------------------*/

Переменные окружения, указанные в файлах ".env", имеют строковой тип.

Чтобы в файлах ".env" указать массив значений для какой-то переменной окружения, эти значения нужно указать через
запятую.

/*--------------------------------------------------------------------------------------------------------------------*/

Для гибкой работы с переменными окружения в NestJS можно использовать следующий вариант:

1. При помощи метода "forRoot()" класса "ConfigModule" из модуля @nestjs/config создать и настроить конфигурационный
динамический модуль:

import { ConfigModule } from '@nestjs/config';

export const configModule = ConfigModule.forRoot({
  envFilePath: [
    process.env.ENV_FILE_PATH?.trim() || '',
    `.env.${process.env.NODE_ENV}.local`,
    `.env.${process.env.NODE_ENV}`,
    '.env.production',
  ].filter(Boolean),
  isGlobal: true,
});

В этом примере:
- В массиве, который указывается в свойстве "envFilePath", приоритет выбора файлов ".env" идет из начала в конец. В
свойстве "envFilePath" также можно просто указать одну строку или не указывать ничего если используется всего один файл
".env" в корне проекта.
- Опция "isGlobal: true" является необязательной и делает модуль "configModule" глобальным.
- Альтернативно этот модуль можно создавать и настраивать прямо в массиве "imports" в модуле "AppModule".

2. Указать созданный конфигурационный модуль в массиве "imports" модуля "AppModule", причем сам импорт в файле должен
быть на самом верху. Поскольку опция "isGlobal: true" сделала модуль "configModule" глобальным, то после импортирования
его в модуль "AppModule" он будет доступен в других модулях.

3. Переменные окружения нежелательно брать напрямую из объекта "process.env", а использовать для этого класс
"ConfigService" из модуля @nestjs/config. Желательно для каждого модуля создавать отдельный файл ".config.ts" и
настраивать в нем работу с переменными окружения для каждого модуля. Далее рассмотрим несколько примеров работы с
переменными окружения.

3.1 Пример "CoreConfig":
- Создаем файл "core.config.ts", который будет содержать переменные, необходимые для общей работы приложения.
- Внутри файла "core.config.ts" создаем класс "CoreConfig".
- Помечаем класс "CoreConfig" декоратором "@Injectable()".
- В параметрах конструктора класса "CoreConfig" передаем экземпляр класса "ConfigService".
- В классе "CoreConfig" создаем поля, описывающие переменные окружения, задавая им значения из файлов ".env", используя
метод "get()" экземпляра класса "ConfigService".
- Поля класса "CoreConfig" помечаем валидационными декораторами из библиотеки class-validator.
- В теле конструктора класса "CoreConfig" вызываем функцию "validateSync()", передав в нее this, чтобы выполнить
синхронную валидацию объекта на основе декораторов, которыми пометили поля класса "CoreConfig". Вызов функции
"validateSync()" можно обернуть в отдельную функцию для обработки ошибок.
- Указываем класс "CoreConfig" в массивах "exports" и "providers" модуля "CoreModule".
- Для использования класса "CoreConfig" с целью настроить параметры MongoDB импортируем модуль "CoreModule" и класс
"CoreConfig" в файл "app.module.ts". В массиве "imports" модуля "AppModule" используем метод
"MongooseModule.forRootAsync()", чтобы создать динамический модуль "MongooseModule". Внутри этого динамического модуля
в массиве "imports" указываем модуль "CoreModule", чтобы из него можно было взять класс "CoreConfig". В массиве "inject"
для внедрения в динамический модуль указываем класс "CoreConfig", который как раз таки и подхватится из
импортированного модуля "CoreModule". Внедренный класс "CoreConfig" используем в методе "useFactory()", чтобы получить
готовый объект настроек.
- Для того, чтобы включать и отключать модуль "TestingModule" в модуле "AppModule" в зависимости от окружения, прямо в
массиве "imports" модуля "AppModule" используем переменную окружения "process.env.NODE_ENV":

...(process.env.NODE_ENV !== Environments.PRODUCTION ? [TestingModule] : []),

Используем здесь именно "process.env.NODE_ENV", а не класс "CoreConfig", так как массив "imports" формируется синхронно
до запуска DI-контейнера и класс "CoreConfig" еще не является созданным на этом этапе, но при это переменная
"process.env.NODE_ENV" уже является доступной, поскольку она задается через команду в терминале.
- Для того, чтобы получить порт в файле "main.ts", вызываем метод "get()" экземпляра приложения NestJS:

const coreConfig: CoreConfig = app.get<CoreConfig>(CoreConfig);

Таким же образом поступаем в файлах "app.setup.ts" и "swagger.setup.ts", так как в этих файлах мы тоже имеем доступ к
экземпляру приложения NestJS.

3.2 Пример "AuthConfig":
- Создаем класс "AuthConfig" для работы с переменными окружения необходимыми для аутентификации и авторизации тем же
образом, что и класс "CoreConfig".
- Создаем вспомогательный модуль "AuthConfigModule" для раздачи переменных из класса "AuthConfig".
- Импортируем модуль "AuthConfigModule" и класс "AuthConfig" в файл "user.module.ts".
- Для задания TTL сущностям "EmailConfirmation" и "PasswordRecoveryCodeData" в массиве "imports" модуля "UserModule"
создаем динамические модули "MongooseModule", используя метод "MongooseModule.forFeatureAsync()". Внутри этих
динамических модулей в массивах "imports" указываем модуль "AuthConfigModule", чтобы из него можно было взять класс
"AuthConfig". В массивах "inject" для внедрения в динамические модули указываем класс "AuthConfig", который как раз таки
и подхватится из импортированного модуля "AuthConfigModule". Внедренный класс "AuthConfig" используем в методе
"useFactory()", чтобы получить готовый объект настроек.
- Для использования класса "AuthConfig" в гардах "BasicAuthGuard" и "JwtAuthGuard" указываем в массиве "imports" модуля
"UserModule" модуль "AuthConfigModule". В файле "basic-auth.guard.ts" в конструкторе класса "BasicAuthGuard" внедряем
класс "AuthConfig", так же как и в файле "jwt-auth.strategy.ts" в конструкторе класса "JwtAuthStrategy". Эти гарды
получат доступ к классу "AuthConfig" через цепочку модулей "UserModule" -> "AuthConfigModule", так как эти гарды указаны
в массиве "providers" модуля "UserModule".
- Для использования класса "AuthConfig" в сервисе "AuthService" так же достаточно того, что модуль "AuthConfigModule"
указывается в массиве "imports" модуля "UserModule".
- Для использования класса "AuthConfig" в других модулях, куда будет импортироваться модуль "UserModule", например, в
модуле "BlogModule", указываем модуль "AuthConfigModule" в массиве "exports" модуля "UserModule".

3.3 Пример "NotificationConfig":
- Создаем класс "NotificationConfig" для работы с переменными окружения необходимыми для работы с уведомлениями тем же
образом, что и класс "CoreConfig".
- Создаем вспомогательный модуль "NotificationConfigModule" для раздачи переменных из класса "NotificationConfig".
- Импортируем модуль "NotificationConfigModule" и класс "NotificationConfig" в файл "notification.module.ts".
- Для задания имени почтового сервиса, адреса почты, используемого для отправки писем, и пароля приложения из Google,
создаем динамический модуль "MailerModule", используя метод "MailerModule.forRootAsync()". Внутри этого динамического
модуля в массиве "imports" указываем модуль "NotificationConfigModule", чтобы из него можно было взять класс
"NotificationConfig". В массиве "inject" для внедрения в динамический модуль указываем класс "NotificationConfig",
который как раз таки и подхватится из импортированного модуля "NotificationConfigModule". Внедренный класс
"NotificationConfig" используем в методе "useFactory()", чтобы получить готовый объект настроек.

/*--------------------------------------------------------------------------------------------------------------------*/

При использовании нескольких вариантов файлов ".env", в командах для запуска приложения нужно задавать переменные
"ENV_FILE_PATH" или "NODE_ENV". Но проблема в том, что, например, для каждой ОС команды будут выглядеть по-разному.
Чтобы решить эту проблему можно использовать пакет cross-env и добавлять в начале команд, например, так:
"cross-env NODE_ENV=development".

/*--------------------------------------------------------------------------------------------------------------------*/

Чтобы при развертывании приложения на сторонних сервисах использовались файлы ".env" нужно сделать следующее:
1. В папке "src" создать папку "env".
2. В папку "env" скопировать все файлы ".env".
3. В файле "nest-cli.json" добавить опцию в разделе "compilerOptions":

"assets": [{ "include": "**/env/*", "watchAssets": true }],

4. Дополнить "configModule":

import { ConfigModule } from '@nestjs/config';
import { join } from 'path';

/*Конфигурационный модуль для работы с файлами ".env".*/
export const configModule = ConfigModule.forRoot({
  envFilePath: [
    process.env.ENV_FILE_PATH?.trim() || '',
    join(__dirname, 'env', `.env.${process.env.NODE_ENV}.local`),
    join(__dirname, 'env', `.env.${process.env.NODE_ENV}`),
    join(__dirname, 'env', `.env.production`),
    `.env.${process.env.NODE_ENV}.local`,
    `.env.${process.env.NODE_ENV}`,
    `.env.production`,
  ].filter(Boolean),

  isGlobal: true,
});
