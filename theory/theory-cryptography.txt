Кодирование - это преобразование данных из одного вида в другой, причем зная алгоритм кодирования можно преобразовать
данные обратно.

Шифрование - это преобразование данных из одного вида в другой, используя какие-то секретные данные, причем зная
алгоритм шифрования и секретные данные можно преобразовать данные обратно.

Хеширование - это преобразование данных из одного вида в другой без возможности преобразовать данные обратно.

/*--------------------------------------------------------------------------------------------------------------------*/

Во многих странах хранение паролей в открытом виде в БД запрещено законодательно. Список данных, которые запрещено
хранить в открытом виде в БД, может быть достаточно большим.

Радужные таблицы - это таблицы паролей и их захешированных версий.

/*--------------------------------------------------------------------------------------------------------------------*/

Поскольку многие сетевые протоколы изначально были созданы для передачи именно текста, кодирование Base64 является очень
популярным при организации обмена данными между приложениями.

/*--------------------------------------------------------------------------------------------------------------------*/

В криптографии используются приватный и публичный ключи:
1. Приватный ключ обычно известен только одной стороне и используется для расшифровывания и подписывания.
2. Публичный ключ обычно может быть известен кому угодно и используется для шифрования и проверки подписей.

Приватный и публичный ключи используются для асимметричного шифрования, то есть для безопасной передачи данных без
предварительного обмена секретами:
1. Одна сторона знает только как зашифровать/подписать, то есть обладает только публичным ключом.
2. Другая сторона знает и как зашифровать/подписать, так и как расшифровать/проверить подпись, то есть обладает
публичным и приватным ключами.

Симметричное шифрование - это быстрое шифрование обычно больших объемов данных. Обе стороны знают как
зашифровать/подписать и расшифровать/проверить подпись. Плюс этого шифрования в быстроте, а не в безопасности (только
если заранее не позаботились о безопасности хранения ключей).

Двустороннее шифрование - это любой тип шифрования, когда данные можно расшифровать. Симметричное шифрование является
одним из типов двустороннего шифрования.

Одностороннее шифрование шифрует данные в одну сторону без возможности расшифровывания. Хеширование можно назвать
односторонним шифрованием.

Гибридное шифрование - это смесь асимметричного и симметричного шифрований. Например, при таком шифровании отправка
архива с данными будет выглядеть примерно так:
1. Отправитель генерирует случайный ключ, например, пароль 123, для симметричного шифрования.
2. Отправитель шифрует архив этим случайным ключом (пароль 123).
3. Получатель отправляет свой публичный ключ отправителю.
4. Отправитель шифрует асимметрично случайный ключ (пароль 123) публичным ключом получателя.
5. Отправитель отправляет зашифрованные случайный ключ (пароль 123) и архив.
6. Получатель расшифровывает своим приватным ключом зашифрованный случайный ключ (пароль 123).
7. Получатель расшифровывает случайным ключом (пароль 123) зашифрованный архив.

/*--------------------------------------------------------------------------------------------------------------------*/

Библиотека bcrypt использует раунды соли - циклическое применение хеш-функции. В этом механизме пароль проходит через
несколько раундов преобразований, где каждый раунд включает в себя применение хеш-функции к результату предыдущего
раунда. Этот процесс повторяется определенное количество раз. Количество применений равно числу 2 в степени равной
количеству раундов соли. Обычно используется 10-12 раундов соли. Циклическое применение хеш-функции делает так, что
время на подбор пароля увеличивается, что усложняет подбор для злоумышленников. Информация о раундах соли, как и об
идентификаторе алгоритма хеширования, добавляется к итоговому хешу: $[algorithm]$[cost]$[salt][hash].

Есть более современный аналог библиотеки bcrypt - Argon2.

Использование современных GPU значительно ускоряет перебор хешей, созданных при помощи библиотеки bcrypt.

Библиотека bcrypt использует только первые 72 байта пароля, игнорируя остальную часть.

При хешировании паролей может использоваться как соль, так и перец:
1. Соль - это случайные данные, уникальные для каждого пароля, которые обычно открыто хранятся в БД вместе с хешем и
используются путем склейки с паролем для дальнейшего хеширования полученной строки. Соль помогает против радужных
таблиц и не дает возможности определить имеют ли несколько пользователей одинаковый пароль, но слабые пароли все еще
могут быть подобраны путем перебора на GPU.
2. Перец - это секретный ключ, один для всех паролей, который обычно хранится отдельно от БД, например, в коде
приложения или переменных окружения, и используется путем склейки с солью и паролем для дальнейшего хеширования
полученной строки. Поскольку перец хранится вне БД, то для взлома паролей злоумышленникам также потребуется вдобавок к
БД украсть еще и код приложения, в котором находится перец. Перец используется вместе с солью и сильно усложняет подбор
паролей путем перебора на GPU.

Библиотека bcrypt использует только соль, когда библиотеки на основе Argon2 могут использовать также и перец (параметр
"secret").

Библиотека bcrypt для своей работы в основном использует CPU и немного RAM (около 4-8 КБ), когда библиотеки на основе
Argon2 по большей части нагружают RAM (например, 64 МБ или 256 МБ), нежели ЦПУ. Именно из-за малого потребления памяти
GPU хорошо справляются с bcrypt, используя сразу несколько ядер для одновременной обработки разных хешей. Библиотеки на
основе Argon2 заполняют гораздо больший объем памяти, чем bcrypt, и в процессе своей работы постоянно обращаются к ней,
из-за чего получается, что множеству ядер GPU сложнее работать с мегабайтами памяти из-за низкой пропускной способности.

Алгоритм хеширования Argon2 имеет 3 версии:
1. Argon2d: оптимизирован против GPU-атак - брутфорса на видеокартах, но уязвим для side-channel атак. Алгоритм
обращается к массиву памяти в порядке, зависящем от пароля, что снижает вероятность атак с компромиссом между временем и
памятью (TMTO), но вносит потенциальные побочные атаки. Быстрее, чем Argon2i. Предпочтителен для криптовалют.
2. Argon2i: оптимизирован против side-channel атак. Алгоритм обращается к массиву памяти в порядке, не зависящем от
пароля. Медленнее, чем Argon2d. Предпочтителен для хеширования паролей и вывода ключей.
3. Argon2id: гибридная версия. Алгоритм использует подход Argon2i для первого прохода по памяти и подход Argon2d для
последующих проходов. RFC 9106 рекомендует использовать Argon2id, если неизвестна разница между типами или если
side-channel атаки считаются реальной угрозой.

В библиотеке node-argon2 в функцию хеширования можно отдать объект с настройками вторым параметром:

1. "hashLength": длина хеша, то есть длина выходных данных хеш-функции в байтах. Результирующий хеш кодируется с
помощью Base64, поэтому результирующий хеш будет примерно на 1/3 длиннее. Значение по умолчанию - 32, что дает
необработанные хеши размером 32 байта или результирующие хеши размером 43 символа.

2. "timeCost": временная стоимость, то есть количество итераций, используемых хеш-функцией. Она увеличивает хеш-силу за
счет времени, необходимого для вычислений. Значение по умолчанию - 3.

3. "memoryCost": объем памяти, используемый хеш-функцией, в KiB (kibibyte = 2^10). Каждый поток будет иметь пул памяти
этого размера. Большие значения для высококонкурентного использования приведут к нехватке ресурсов и снижению
производительности, если системная память заполнится. Значение по умолчанию - 65536, что означает пул в 64 MiB
(mebibyte = 2^20) на поток.

4. "parallelism": Количество потоков для вычисления хеша. Каждый поток имеет пул памяти размером, указанным в параметре
"memoryCost". Изменение этого параметра также изменяет результирующий хеш. Значение по умолчанию - 4, что означает
использование 4 потоков.

5. "type": вариант хеш-функции - Argon2d, Argon2i или Argon2id.

6. "secret": дополнительные данные, используемые в процессе хеширования, которые не включаются в хеш, как, например,
соль. Они должны быть достаточно случайными и непредсказуемыми, а также надежно храниться, чтобы предотвратить
компрометацию. Секрет должен представлять собой экземпляр объекта Buffer. Значение по умолчанию не задано.

7. "associatedData": дополнительное и необязательное несекретное двоичное значение. Значение будет включено в раздел
параметров результирующего хеша в кодировке Base64. Значение по умолчанию не задано.

8. "raw": определяет, будет ли вывод представлять собой результирующий хеш или необработанный хеш до кодирования Base64.
Если установить этот параметр в значение true, то не будет возможности использовать метод "verify()" для проверки
пароля. Значение по умолчанию - false. Этот параметр предназначен для строго специфичных целей. Никогда не стоит его
использовать для хеширования паролей, так как отклонение от значений по умолчанию снизит уровень безопасности.

9. "version": версия Argon2 для использования. В настоящее время доступны версии 1.0 (0x10) и 1.3 (0x13). Изменять это
не следует, так как последняя версия более мощная. Значение по умолчанию - 0x13 (19) для Argon2 1.3. Этот параметр
предназначен для строго специфичных целей. Никогда не стоит его использовать для хеширования паролей, так как отклонение
от значений по умолчанию снизит уровень безопасности.

10. "salt": соль. Не стоит указывать собственную соль, если точно неизвестно, как она работает и что означает. Соль
используется для защиты данных от радужных таблиц. Не следует устанавливать собственную соль (она уже хранится в хеше).
Значение по умолчанию - не задано, что генерирует криптографически безопасную случайную соль. Этот параметр предназначен
для строго специфичных целей. Никогда не стоит его использовать для хеширования паролей, так как отклонение от значений
по умолчанию снизит уровень безопасности.

TLS - это протокол шифрования, обеспечивающий безопасную передачу данных, шифруя их. HTTPS - это HTTP-протокол,
работающий поверх TLS.

Преимущества HTTPS:
1. Конфиденциальность: никто не может подслушать, какие данные передаются.
2. Целостность: передаваемые данные нельзя подменить по пути.
3. Аутентификация: гарантия, что общение происходит с нужным сайтом, а не с подделкой.
4. SEO: Google ранжирует HTTPS-сайты выше.
5. Современные API: многие новые веб-технологии (Service Workers, Geolocation, Push-уведомления) требуют HTTPS.

При логинизации клиент может получать уникальный зашифрованный токен, который будет предъявляться при работе с сайтом.
При помощи этого токена может идентифицировать пользователя на разных запросах. Такие токены прикрепляются к запросам.

Клиент может получить токен, например, через cookies (полученных от сервера), в теле ответа сервера или в
HTTP-заголовках (более редкая ситуация).

JWT - это открытый стандарт (RFC 7519), используемый для передачи информации. Он часто используется для аутентификации и
авторизации в веб-приложениях.

JWT состоит из 3 частей:
1. Заголовок (Header): содержит информацию о типе токена и алгоритме шифрования, используемом для его подписи. Обычно
заголовок выглядит так: { "alg": "HS256", "typ": "JWT" }.

2. Полезная нагрузка (Payload): содержит данные (claims - утверждения) о пользователе или другую информацию, которую
необходимо передать клиенту. Есть три типа утверждений:
2.1 Зарезервированные утверждения (Registered claims): включают стандартные поля, такие как "iss" (выдавший токен),
"iat" (время выдачи токена), "exp" (срок действия токена), "sub" (субъект токена) и другие.
2.2 Пользовательские утверждения (Public claims): содержат информацию, специфичную для вашего приложения.
2.3 Приватные утверждения (Private claims): пользовательские утверждения, которые согласованы между двумя сторонами и не
включены в стандартные имена полей.
Пример полезной нагрузки: { "sub": "1234567890", "name": "John Doe", "admin": true, "iat": 1516239022 }.

3. Подпись (Signature): используется для проверки подлинности и целостности токена. Представляет собой хеш склейки
заголовка и полезной нагрузки.

Процесс формирования JWT токена:
1. Создается JSON-объект для заголовка.
2. Создается JSON-объект для полезной нагрузки.
3. Кодируется заголовок алгоритмом Base64url (более безопасен для URL-адресов, имен файлов и HTTP-заголовков).
4. Кодируется полезная нагрузка алгоритмом Base64url.
5. Соединяются закодированные заголовок и полезная нагрузка в одну строку через точку.
6. Создается подпись путем хеширования полученной строки алгоритмом, указанным в заголовке, используя секретный ключ
6. Создается подпись путем хеширования полученной строки алгоритмом, указанным в заголовке, используя секретный ключ
(перец).
7. Кодируется подпись алгоритмом Base64url.
8. Соединяются закодированные заголовок, полезная нагрузка и подпись в одну строку через точку, формируя тем самым JWT.

Приложение при помощи секретного ключа и алгоритма хеширования может проверить подлинность токена.

JWT может использоваться для общения между бэкендами, например, с платежными системами.

Одним из самых популярных способов хранения JWT на клиенте является local storage, так как у JS есть доступ к нему.

Примерный порядок работы с JWT между клиентом и бэкендом:
1. Клиент делает запрос на endpoint для аутентификации пользователя, указывая в теле запроса логин и пароль.
2. Бэкенд получает тело запроса и проверяет логин и пароль пользователя - если с ними есть проблемы, то бэкенд
отправляет клиенту ответ на запрос и в теле ответа сообщает об отказе в аутентификации, иначе бэкенд создает Access
Token (JWT) и отправляет клиенту ответ на запрос, в теле которого указывается AT.
3. Клиент получает ответ на запрос, извлекает из него AT и сохраняет его в local storage.
4. Клиент делает запрос на какой-то другой endpoint, указывая в теле запроса AT.
5. Бэкенд получает тело запроса и проверяет AT в специальном middleware - если с AT есть проблемы, то бэкенд отправляет
клиенту ответ на запрос и в теле ответа сообщает об отказе в аутентификации, иначе бэкенд выполняет необходимую операцию
в соответствии с endpoint (если не было других проблем, например, при авторизации) и отправляет клиенту корректный ответ
на запрос.

Webhook - это как callback-функции, только для приложений, то есть, когда одно приложение автоматически отправляет
данные другому приложению в реальном времени, как только происходит какое-то событие. Например, если бэкенд общается с
какой-то платежной системой, то та в ответ на выполнение каких-то платежных операций будет сообщать бэкенду о них через
открытое API бэкенда, используя JWT, который будет верифицироваться бэкендом.

Популярные случаи использования JWT:
1. Аутентификация и авторизация пользователей.
2. Аутентификация и авторизация ботов и AI-агентов.
3. Обмен данными между сервисами - JWT содержит полезные данные о какой-то операции, срок действия, а также возможность
проверки подлинности.
4. Одноразовая или временная авторизации - в ссылку встраивается JWT и она, например, отправляет на почту пользователя.
5. Единый вход для экосистем приложений, например, как у Google - JWT используется в формате ID-токена в протоколе
OpenID Connect (надстройка над OAuth 2.0).

JWT использует алгоритм HS256, который использует симметричное шифрование (подписывание HMAC):
1. Бэкенд в данном случае является и тем, кто подписывает, и тем, кто проверяет подпись.
2. Бэкенд использует один и тот же ключ как для подписи, так и для проверки.

HMAC (Hash-Based Message Authentication Code) - это код аутентификации сообщения на основе хеш-функции. HMAC
используется для подписания данных при помощи секретного ключа, чтобы получатель мог проверить, что:
1. Данные не были подделаны по пути.
2. Данные были получены действительно от того, у кого есть секретный ключ.

В целях безопасности вдобавок к AT может использоваться Refresh Token (RT). AT используется для доступа к ресурсам и AT
должен иметь короткий срок действия, в отличие от RT. Когда у AT почти истекает срок действия, клиент должен отправлять
RT на специальный endpoint, чтобы получить новую пару AT и RT. Старый RT при этом становится недействительным, а текущий
AT может оставаться еще рабочим.

RT должен быть защищен сильнее, чем AT. В БД можно хранить список всех недействительных RT, чтобы если злоумышленник
смог воспользоваться одним из них, то он не мог получить новую пару AT и RT.

Но если злоумышленник все-таки смог воспользоваться актуальной парой AT и RT, то он сможет получить новую пару AT и RT,
когда пользователь будет владеть еще старой парой AT и RT. Это приведет к тому, что пользователю придется вводить
повторно свои учетные данные, чтобы получить новую актуальную пару AT и RT. В таком случае, можно сохранять в БД список
устройств и браузеров, с которых была произведена авторизация, чтобы, когда пользователь снова вводил свои учетные
данные, ему был доступен список устройств и браузеров, прошедших авторизацию, и он мог отозвать авторизации с
неизвестных для него устройств и браузеров.

RT стоит хранить в cookies с флагом "HTTPonly", который не позволяет любому JS-коду иметь доступ к ним. RT может быть
сделан в формате, отличном от JWT. AT часто хранится в local storage, так как клиент может использовать открытые данные
из AT.

Почему использование пары AT и RT безопаснее использования только лишь AT:
1. Используем только AT, передаем его через cookies с флагом "HTTPonly" и устанавливаем ему долгий срок действия,
например, 7 дней:
1.1 Если украли AT, то злоумышленник сможет им пользоваться вплоть до 7 дней.
1.2 Пользователь не будет знать, что AT украли, вплоть до 7 дней.
1.3 Пользователь получит новый AT только когда еще раз пройдет логинизацию, при этом если на бэкенде не реализован
черный список для AT, то сворованным AT также продолжит пользоваться злоумышленник.
1.4 Если на бэкенде реализован перевыпуск AT на основе предыдущего AT, то злоумышленник сможет бесконечно перевыпускать
AT до тех пор, пока пользователь не попробует перевыпустить AT.
2. Используем пару AT и RT, AT передаем через тело ответа и устанавливаем ему короткий срок действия (например, 1 час),
RT передаем через cookies с флагом "HTTPonly" и устанавливаем ему долгий срок действия (например, 7 дней):
2.1 Если украли AT, то злоумышленник сможет им пользоваться не больше 1 часа.
2.2 Пользователь не будет знать, что AT украли, не больше 1 часа.
2.3 Злоумышленник не сможет получить новый AT, не украв RT.
2.4 Если украли пару AT и RT, то злоумышленник сможет им пользоваться не больше 1 часа.
2.5 Как только злоумышленник сделает новую пару AT и RT, пользователя разлогинит и ему придется пройти логинизацию,
чтобы получить более новую пару AT и RT, что сделает новый RT злоумышленника недействительным.

Работу с аутентификацией и авторизацией можно выделять в отдельный сервер, чтобы распределить нагрузку, повысить
безопасность путем снижения связанности с ресурсными серверами, позволить регистрацию сразу для нескольких приложений
через один авторизационный сервер.

Чтобы ресурсные серверы могли проверять валидность AT, им нужно знать только секрет, используемый при создании
JWT-токена. Актуальные пары AT и RT лучше не хранить в БД, так как сервера могут и без них проверять подлинность AT и
RT. Если все-таки есть необходимость хранить актуальный RT в БД, то можно хранить только его 1 и 2 части, так как
злоумышленники по сути будут иметь только лишь неподписанный токен и не обладать секретом, используемым для подписания
токена.

Вместо RT в БД можно хранить информацию касательно RT: дата выдачи RT, ID и имя устройства, IP-адрес, ID пользователя.
При этом дата выдачи RT является главным полем, определяющим RT в БД. Когда клиенту требуется новый RT, то можно
требовать от клиента прислать ID его устройства, чтобы после генерации нового RT в БД найти запись по ID устройства и
обновить дату выдачи RT. Такой механизм лучше, так как список недействительных RT будет увеличиваться бесконечно.

При получении новой пары ATи RT клиент может также отправлять ID устройства, чтобы по нему и по дате выдачи последнего RT
можно было проверить валидность присланного от клиента RT. В итоге для каждого авторизованного устройства и браузера в
БД будет храниться отдельная сессия. Когда пользователь выходит из приложения, нужно удалять соответствующую
авторизационную сессию из БД.

При проверке RT может быть тяжело определить используется ли сейчас браузер, который использовался в момент создания RT,
так как, например, браузеры достаточно часто обновляют версии. В таком случае можно анализировать другие характеристики,
например, разрешение экрана в браузере или поведение пользователя в браузере.

Если на нашей стороне было определено, что произошла утечка данных пользователя и пользователь все еще пользуется
старыми учетными данными, то мы можем удалить все авторизационные сессии пользователя сами и сообщить пользователю о
необходимости обновить учетные данные.

Порядок работы с AT и RT в версии приложения с использованием Express.js и MongoDB (ДО ИСПОЛЬЗОВАНИЯ СЕССИЙ):
1. Пользователь вводит свои учетные данные, формируя запрос на endpoint "/auth/login" для получения пары AT1 и RT1.
2. Бэкенд создает пару AT1 и RT1 и отправляет их в ответе клиенту. AT отправляются через тело ответа клиенту, RT - через
cookies. Срок действия AT - 10 секунд, RT - 20 секунд. Все действующие RT сохраняются в БД как белый список, а
недействующие - как черный список. Белый и черный списки должны периодически очищаться от недействующих RT.
3. Пользователь, после получения пары AT1 и RT1, использует AT1 в заголовках запросов для совершения операций на сайте.
4. Когда истекает срок действия AT1, пользователь делает запрос на endpoint "/auth/refresh-token" для получения новой
пары AT2 и RT2, указывая RT1 в cookies.
5. Бэкенд, получив запрос от клиента, проверяет RT1.
6. Если RT1 находится в черном списке, отсутствует в белом списке или его срок действия истек, то бэкенд не создает
новую пару AT2 и RT2 - клиенту придется снова вводить свои учетные данные для получения новой пары AT2 и RT2.
7. Если RT1 не находится в черном списке, есть в белом списке и его срок действия еще не истек, то бэкенд создает новую
пару AT2 и RT2, отправляя AT2 в теле ответа клиенту, RT2 - через cookies, а затем убирает RT1 из белого списка и
помещает его в черный список.
8. Далее повторяются шаги 3-7, но уже с парой AT2 и RT2.
9. Отдельно, если пользователь захочет выйти из системы, то он может отправить запрос на endpoint "/auth/logout",
указав текущий RT в cookies. В ответ бэкенд уберет текущий RT из белого списка и поместит его в черный список.

В рамках безопасности иногда можно менять секрет для JWT, но нужно понимать, что это приведет к разлогинизации всех
пользователей, так как все их пары AT и RT станут невалидными. Чтобы сгладить этот момент, можно некоторое время держать
предыдущий и новый секрет, чтобы пользователи могли пользоваться еще старыми валидными парами AT и RT (graceful
rotation).

Декодирование JWT дешевле, чем его верификация, так как декодирование - это перевод из Base64 в строку, а верификация -
это более тяжелый процесс проверки.

Сессия - это интервал времени, в рамках которого пользователь пользуется приложением. В БД можно сохранять данные
сессии, то есть информацию о любой активности пользователя в рамках какой-то сессии. В зависимости от данных сессии
можно либо создавать новые сессии, либо продлевать старые.

Поскольку протокол HTTP является stateless, то сессии тоже могут решить эту проблему, поскольку они позволяют сохранять
некое состояние между запросами. Сессии позволяют аутентифицировать пользователей, хранить пользовательские предпочтения
(настройки и персонализация), отслеживать действия пользователя.

Если пользователь пользуется сайтом без логинизации, то можно использовать анонимную сессии, генерировать для нее ID и
передавать его через cookies или HTTP-заголовки. ID такой сессии можно хранить в БД и делать в виде JWT или UUID. ID
сессии должен быть таким, чтобы его можно было проверить на подлинность. У ID сессии должен быть срок действия. Обычно
ID сессии хранится в cookies в свойстве "Session". Каждый приход одного и того же ID сессии должно являться триггером
для продления этой сессии.

Анонимные сессии позволяют отслеживать данные для маркетинга, анализировать поведение пользователей, идентифицировать
ботов и попытки взлома, улучшать работу с приложением для потенциальных пользователей (например, работа с корзиной до
регистрации пользователя, хотя корзину можно сделать и через localstorage).

Отсутствие cookies и сессий у пользователя является триггером для создания анонимной сессии.

Время сессии может продлеваться после каждого запроса пользователем (sliding expiration).

Для работы с сессиями в Express.js можно использовать библиотеку express-session.

Использование сессий вместе с парой AT и RT более безопасно, так как для RT придется вести черный и/или белый списки,
которые могут быть украдены. Используя сессии, в БД можно хранить не сами RT, а какую-то менее чувствительную информацию
о них, например, дату выдачи, дату истечения, версию RT.

Один из простых вариантов ведения сессий:
1. В БД вести таблицу: ID пользователя, ID устройства, версия RT (любой формат).
2. При генерации RT в payload указывать данные из таблицы.
3. При каждом перевыпуске RT обновлять версию RT в БД, чтобы можно было валидировать RT.

Сессии в основном строятся вокруг связи ID пользователя и устройства. Добавление IP-адреса к перечисленным данным
увеличивает безопасность, но также может создавать больше проблем для пользователя, если он, например, использует VPN.
В современных приложениях часто делают так: при смене IP-адреса, если устройство осталось прежним, то просто обновляют
IP-адрес в данных о сессии, чтобы пользователь мог дальше продолжать работу в рамках текущей сессии.

Имя устройства можно брать из HTTP-заголовков.

Любая логинизация должна приводить к созданию новой сессии.

Не всегда можно идентифицировать точно клиента - какие-то механизмы работы с сессиями иногда приходится основывать на
доверии.

Если есть необходимость, то благодаря сессиям можно ограничивать количество устройств, с которых можно одновременно
пользоваться приложением.

В рамках безопасности стоит уведомлять пользователя, например, по почте, о логинизации с нового устройства.

Если злоумышленник украл cookies и попытался зайти с другого устройства, то это будет означать, что устройство в данных
о сессии будет не совпадать с устройством в HTTP-заголовках. В таком случае нужно сразу удалять сессию.

Порядок работы с AT и RT и сессиями в версии приложения с использованием Express.js и MongoDB:
1. Пользователь вводит свои учетные данные, формируя запрос на endpoint "/auth/login" для получения пары AT1 и RT1 и
создания новой сессии.

2. Бэкенд получает IP-адрес пользователя и имя устройства пользователя из HTTP-заголовков запроса, логин/email и пароль
из тела запроса, генерирует ID для устройства пользователя, получает ID пользователя из БД по полученным учетным данным
пользователя, генерирует RT1 на основе ID пользователя и ID устройства, генерирует AT1 на основе ID пользователя.

3. Бэкенд создает в БД запись о новой сессии с указанием в ней следующих данных: ID пользователя, ID устройства, имя
устройства, IP-адрес, дата выдачи RT, дата истечения RT.

4. Бэкенд создает в БД запись о новом устройстве пользователя с указанием в ней следующих данных: ID устройства, имя
устройства, IP-адрес, дата выдачи RT.

5. Бэкенд отправляет пару AT1 и RT1 в ответе клиенту. AT отправляются через тело ответа клиенту, RT - через cookies.
Срок действия AT - 10 секунд, RT - 20 секунд.

6. Пользователь, после получения пары AT1 и RT1, использует AT1 в HTTP-заголовках запросов для совершения операций на
сайте.

7. Когда истекает срок действия AT1, пользователь делает запрос на endpoint "/auth/refresh-token" для получения новой
пары AT2 и RT2, указывая RT1 в cookies.

8. Бэкенд, получив запрос от клиента, проверяет RT1.
8.1 Если в заголовках запроса нет имени устройства пользователя, то бэкенд не создает новую пару AT2 и RT2.
8.2 Если в заголовках запроса нет IP-адреса пользователя, то бэкенд не создает новую пару AT2 и RT2.
8.3 Если в cookies запроса нет RT1, то бэкенд не создает новую пару AT2 и RT2.
8.4 Если RT1 не является валидным, то бэкенд не создает новую пару AT2 и RT2.
8.5 Если RT1 в payload содержит ID пользователя, который не указан ни в одном пользователе в БД, то бэкенд не создает
новую пару AT2 и RT2.
8.6 Если RT1 в payload содержит ID устройства, который не указан ни в одном устройстве в БД, то бэкенд не создает новую
пару AT2 и RT2.
8.7 Если по ID пользователя из payload в RT1, ID устройства пользователя из payload в RT1 и дате выдачи RT1 в БД нет ни
одной сессии, то бэкенд не создает новую пару AT2 и RT2.
8.8 Если проблем с RT1 выявлено не было, то:
8.8.1 Бэкенд генерирует RT2 на основе ID пользователя и ID устройства из payload в RT1.
8.8.2 Генерирует AT2 на основе ID пользователя из payload в RT1.
8.8.3 По дате выдачи RT1 находит сессию в БД и обновляет в сессии дату выдачи RT, дату истечения RT и IP-адрес.
8.8.4 По ID устройства пользователя из payload в RT1 находит устройство в БД и обновляет в устройстве IP-адрес и
последнюю дату использования (дата выдачи RT2).
8.8.5 Отправляет AT2 через тело ответа клиенту.
8.8.6 Отправляет RT2 через cookies в ответе клиенту.

9. Далее повторяются шаги 6-8, но уже с парой AT2 и RT2.

10. Отдельно, если пользователь захочет отозвать сессию, то он может отправить запрос на endpoint "/auth/logout" с
действующим RT в cookies запроса. Этот RT пройдет проверки как в шаге 8 и если проблем с RT выявлено не будет, то бэкенд
по дате выдачи RT найдет сессию в БД и удалит ее.

11. Дополнительно БД настроена так, чтобы автоматически удалять сессии, у которых истек срок действия RT.
