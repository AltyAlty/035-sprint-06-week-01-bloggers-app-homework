которые могут конфликтовать с форматировщиком кода Prettier.

линтинга ESLint. Обеспечивает использование форматировщика кода Prettier как ESLint-правила, что позволяет

При работе с пакетами InversifyJS и reflect-metadata при помощи декоратора "@injectable()" помечается сущность, которая
может быть куда-то внедрена, а при помощи декоратора "@inject()" помечается то, что должно быть внедрено.

Чтобы обойти циклическую зависимость вместо декоратора "@inject()" можно использовать приватный геттер (паттерн Lazy
Loading, хотя обращение внутри класса к IoC-контейнеру является антипаттерном Service Locator):

private get postsService() {
    return container.get(PostsService);
  }

Альтернативно для решения проблемы с циклической зависимостью можно использовать пакет inversify-inject-decorators. Он
позволяет создавать декоратор "@lazyInject()", реализующий lazy loading, чтобы избежать создания экземпляра одного
класса внутри конструктора другого класса, что как раз и вызывает замкнутый круг зависимостей между двумя классами.
Поэтому декоратор "@lazyInject()" нужно указывать вне конструктора класса.

Чтобы Jest работал с InversifyJS нужно:
1. Установить Ядро компилятора Babel.
2. Установить пресет плагинов, позволяющий Babel транспилировать современный синтаксис JS в более старый.
3. Установить пакет, сообщающий Jest как надо использовать Babel.
4. Добавить в файл "jest.config.ts", чтобы Jest заставлял Babel транспилировать код InversifyJS:
transformIgnorePatterns: ['node_modules(?!.*(?:inversify|@inversifyjs))'],
  transform: {
    '\\.tsx?$': 'ts-jest',
    '\\.js$': ['babel-jest', { presets: ['@babel/preset-env'] }],
  },

Это приходится делать, так как Jest по умолчанию игнорирует папку "node_modules", то есть считает, что весь код в этой
папке уже скомпилированным обычным JS и пытается просто выполнять его. Но InversifyJS выполнен в виде современного
ES-модуля (ESM), используя современный синтаксис JS, когда Jest ожидает старый формат (CommonJS). Поэтому настраиваем
так, чтобы Jest не игнорировал папку "node_modules", а Babel транспилировал код InversifyJS при запуске тестов.

Библиотека class-transformer может превращать данные запроса, типизированные каким-то DTO, в экземпляр класса этого DTO,
чтобы передать этот экземпляр библиотеке class-validator для дальнейшей валидации.

Библиотека class-transformer позволяет:
1. Превращать сырой JSON из запроса в объект с методами класса при помощи метода "plainToInstance()".
2. Скрывать чувствительные данные при отправке ответа клиенту при помощи декоратора "@Exclude()".
3. Изменять значения на лету при помощи декоратора "@Transform()".
4. Переименовывать поля при сериализации или десериализации при помощи декоратора "@Expose({ name: 'user_id' })".
5. Указывать типы для вложенных объектов и массивов при помощи декоратора "@Type(() => Class)", чтобы они тоже
становились экземплярами нужных классов.
6. Управлять видимостью полей в разных контекстах (например, для разных типов пользователей), используя группы:
"@Expose({ groups: ['admin'] }) и @Exclude({ groups: ['user']) })".
7. Игнорировать лишние поля из входного объекта, которых нет в классе, используя опцию "excludeExtraneousValues: true".
8. Преобразовывать экземпляр обратно в обычный объект методами "instanceToPlain()" или "classToPlain()" (устаревший) для
отправки клиенту, применяя все правила.

Декоратор "@Type()" из библиотеки class-transformer делает так, что когда создается экземпляр класса, свойство
помеченное декоратором "@Type()" будет преобразовано в указанный целевой тип. В какой целевой тип нужно сделать
преобразование библиотека class-transformer поймет при помощи callback-функции, указанной в декораторе.

Библиотека class-validator предоставляет следующие декораторы, образующие цепочку проверок:
1. "@IsOptional()" помечает поле как необязательное, чтобы при его отсутствии не было ошибки и проверка пошла дальше.
Указывается всех ближе к проверяемому полю, чтобы при отсутствии значения для этого поля не запускались остальные
валидационные декораторы.
2. "@IsInt()" проверяет, что значение является целым числом.
3. "@Min(1)" проверяет, что числовое значение больше или равно 1.
4. "@IsEnum(enum)" проверяет, что значение существует внутри указанного enum.
5. "@IsString()" проверяет, что значение является строкой.
6. "@IsNotEmpty()" проверяет, что значение не является пустой строкой, null или undefined.
7. "@Length(min, max)" проверяет, что количество символов в строке находится в указанном диапазоне.
8. "@IsUrl()" поверяет, что строка является валидным веб-адресом.
9. "@IsEmail()" проверяет, что строка соответствует международному стандарту email-адресов.
10. "@Matches(regex)" проверяет, что строка соответствует указанному регулярному выражению.
11. "@IsMongoId()" проверяет, что строка соответствует формату ObjectId, используемому в MongoDB.

При выборе стратегии для аутентификации при использовании библиотеки Passport.js нужно устанавливать дополнительные
пакеты для выбранной стратегии. Чтобы использовать выбранную стратегию, нужно:
1. Импортировать "PassportStrategy" из библиотеки @nestjs/passport.
2. Импортировать "Strategy" из дополнительного пакета для выбранной стратегии, например, из пакетов passport-local или
passport-jwt.
3. Создать класс для выбранной стратегии путем наследования от "PassportStrategy", в который свою очередь нужно передать
"Strategy".
4. Пометить декоратором "@Injectable()" созданный класс для выбранной стратегии.
5. Реализовать метод "validate()", который будет автоматически вызываться библиотекой Passport.js для валидации учетных
данных пользователя. Результат работы этого метода будет помещен в свойство "user" объекта запроса, то есть в объект
"req.user".
6. В зависимости от выбранной стратегии могут понадобиться дополнительные шаги.
7. Указать в массиве "providers" модуля созданную стратегию.
8. Импортировать "AuthGuard" из библиотеки @nestjs/passport.
9. Создать класс для гарда для выбранной стратегии путем наследования от "AuthGuard", в который свою очередь нужно
передать строковой параметр, обозначающий выбранную стратегию, например, "local" или "jwt". Альтернативно можно не
создавать отдельный гард, а использовать, например, такое: "@UseGuards(AuthGuard('jwt'))".
10. Пометить декоратором "@Injectable()" созданный класс для гарда.
11. Использовать созданный гард в нужном месте при помощи декоратора "@UseGuards()".

В модулях, где будут использоваться созданные гарды, нужно импортировать класс "PassportModule" из модуля
@nestjs/passport, используя метод "register()" этого класса.

Класс "MailerService" из модуля @nestjs-modules/mailer - это главный провайдер, который инжектируется в сервисы для
отправки почты. Экземпляры класса "MailerService" из модуля @nestjs-modules/mailer содержат встроенный метод

Класс "MailerModule" из модуля @nestjs-modules/mailer - это главный провайдер, который инжектируется в модули для

Для настройки ограничения частоты запросов при помощи модуля @nestjs/throttler, нужно сделать следующее:
1. Инициализировать модуль и задать настройки по умолчанию в массиве "imports" модуля "AppModule":

ThrottlerModule.forRootAsync({
      imports: [CoreModule],
      inject: [CoreConfig],
      useFactory: (coreConfig: CoreConfig) => [
        { ttl: coreConfig.REQUEST_RATE_LIMIT_TTL * 1000, limit: coreConfig.REQUEST_RATE_LIMIT },
      ],
    }),

2. Создать кастомный гард, который переопределяется стандартное поведение метода, отслеживающего запросы - по умолчанию
он отслеживает только IP-адрес, а нам нужно, чтобы он отслеживал связку IP-адреса и эндпоинта:

import { Injectable } from '@nestjs/common';
import { ThrottlerGuard } from '@nestjs/throttler';
import { DomainException, DomainExceptionCode } from '../../exceptions/domain/domain.exception';

@Injectable()
export class RequestRateLimitingGuard extends ThrottlerGuard {
  protected async getTracker(req: Record<string, any>): Promise<string> {
    return Promise.resolve(`${req.ip}:${req.method}:${req.path}`);
  }

  protected throwThrottlerException(): Promise<void> {
      throw new DomainException({ code: DomainExceptionCode.TooManyRequests, message: 'Too many requests', field: 'ip' });
    }
}

3. Использовать кастомный гард в методах контроллера вместе с декоратором "@Throttle()" для переопределения настроек по
умолчания, указанных в модуле "AppModule":

@UseGuards(RequestRateLimitingGuard)
@Throttle({ default: { limit: 2, ttl: 10000 } })

Для написаний сырых запросов для PostgreSQL можно использовать класс "DataSource" из TypeORM, путем внедрения его
экземпляров в конструкторы классов репозиториев при помощи декоратора "@InjectDataSource()" из модуля @nestjs/typeorm.

TypeORM не всегда может преобразовать сложный запрос в тот, который именно нужен.
